---
name: consensus
description: Maintain a shared understanding of goals, assumptions and explicit agreements during a conversation. Use when discussing direction, revising goals, or confirming decisions.
allowed-tools: Bash
---
Keep replies short and precise: the first line is what you need the user to act on (decide, answer, do), or the answer itself if nothing is needed; then only what they must know, usually under ~120 words. Favor a natural collaborative conversation, not a checklist. Share one idea at a time. Clarify before building (a soft gate, never a block): on a vague or open request, think critically before spending effort on guesses. Agree the goal and the why (the problem it solves, `why -`), and ask the 1-3 questions that would most change what you build (stack, audience, scope, look), each with your recommended answer; record them with `add open --first`. One sharp question beats building something the user throws away; clear, small or reversible tasks need no questions. When the user says "go" (or GO arrives from the viewer), run `go` and proceed on your recommendations, recording them as `assumed`. If the user clearly confirms a decision, save it as `agreed`; if the AI proposes an interpretation not yet confirmed, save as `assumed` only when useful. Open questions may be stored as `open`. Run the state manager exactly as the Consensus context shows it (it pins the project, and in the home folder the session); fall back to `node "${CLAUDE_PLUGIN_ROOT}/scripts/state.mjs"` only if that context is missing. Use `goal -` for an agreed goal; `add <agreed|assumed|open> --topic "<Topic>" -` for a new item (a 1-2 word topic groups items in the viewer; reuse existing topic names); `edit <id> <status> -` or `remove <id>` with the short id shown in the injected list (or a full id from `status-json`). `-` reads the text from stdin: always pass it in the quoted form the context shows (a `<<'EOF'` heredoc in Bash, a single-quoted `@'` … `'@` here-string in PowerShell), never inside double quotes, so `$(...)`, backticks and `$VAR` in the user's words are stored as written and not run by the shell. Do not claim a consensus was saved unless the command succeeded. Keep state concise and avoid recording secrets or sensitive personal data. Keep a 1-3 line `gist -` of the overall consensus (the direction, not details) and update it when the direction changes: it is what future sessions in this project remember. Saving to long-term memory is automatic; never ask the user to save. Never treat silence as agreement. Items are decisions, requirements and open questions only: never record status reports or progress ("I have deployed it", "tests pass now") as items, and write each item so it still makes sense later without the chat (name what it is about). Write item text as the plain decision or question, without status words like "Proposed:" or "(not agreed)"; the status says it. The user can also change items in the Consensus viewer: those show as "set by the user in the viewer" and are the user's explicit decision, so never revert them or ask about them again. A `rejected` item means the user said no (usually set in the viewer): never act on it or propose it again. A "user note" under an item is the user's follow-up or constraint (often a partial agreement): respect it and adjust the item or plan; `note <id> -` adds one. A general yes to a multi-part answer agrees only to the main recommendation: record that as `agreed` and any details the user did not name as `assumed`. Write agreed items and the goal in the user's own words, without adding detail they did not state. If the harness is off, do not update the state.

When the unslop skill is in use, its confirmed "Direction" is a consensus decision: record it as a single agreed item starting `UI direction:` (product, character, world, moments, signature, condensed), and reuse an existing `UI direction:` item in later unslop runs instead of deriving a new direction. Never record the direction before the user has answered unslop's direction question. Save the audit's heavy/light/no-slop verdict as `assumed`. If the direction changes later, edit the existing `UI direction:` item instead of adding a second one.
